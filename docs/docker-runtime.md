# Docker 运行版本和升级策略

本组在第4组更新/重启功能之上增加容器启动器，保留所有内置任务和音乐合伙人配置。无需插件；不修改已有账号 Cookie、WebUI 密码及定时任务。

## 运行和恢复

镜像内程序固定在 `/opt/ncmm/ncmm`，`ncmm-launcher` 监督 Web 进程。`/usr/local/bin/ncmm` 是统一入口，CLI、WebUI 子任务和旧 cron 使用同一份已确认运行版本。运行槽位存于 `/data/runtime/versions/<版本>-<摘要前16位>/ncmm`；`state.json` 记录 current、previous、pending、SHA256、镜像摘要和失败原因。

更新下载、格式及原生发布来源验证仍沿用现有更新器。受管容器把新文件写入 pending，不覆盖运行文件。WebUI 重启通过退出码75通知启动器；新进程必须在30秒内连续两次通过回环 `/api/v1/instance`，PID、实例ID及版本均须匹配。确认后才切换 current 和统一CLI入口，并保留 previous。启动崩溃、版本不符、超时或确认后的异常退出会尝试回退一次；回退也失败则退出容器供运维处理，不无限重启。外部停止会终止并回收子进程。

相同坏文件摘要不会再次暂存，自动更新也不反复下载已拒绝的安装回执；较新发布可继续尝试。状态和WebUI保留回滚原因。只保留当前、上一版及等待中的程序槽位，清理不递归删除用户附加文件，旧槽位仅留下稳定锁文件以免破坏进程互斥。首次启动或状态损坏使用镜像程序恢复；较旧镜像不会覆盖数据卷中较新的有效版本，新镜像或同版本重建通过健康检查后才启用。

`NCMM_RUNTIME_DIR` 默认 `/data/runtime`，必须是规范绝对路径。不要让多个 Web 容器共享同一运行目录；启动器有独占锁。无启动器标记的旧容器仍拒绝原地更新，应先用本仓库 Dockerfile 重建。已有 Compose 的 `NCMM_UPDATER_AUTO_UPDATE=false` 继续有效，手动更新仍可使用。

仅 `web` 模式提供在线健康确认与版本切换。纯CLI/旧crond模式始终使用 current；可暂存更新，但须启动Web模式完成确认，或重建镜像。不要把“文件已下载”当作该版本已启用。

## 原生发布的升级要求

仅识别本仓库 `v主.次.补丁-grails` 及历史 `v主.次.补丁-grails.修订` 版本、Grails125/ncmm 发布来源以及 Release 正文中的显式标记：

```text
<!-- ncmm-force-upgrade -->
```

普通发布、上游 `v1.2.9`、未知版本和无标记发布不会触发强制要求。发布后按 `published_at.AddDate(0,1,0)` 留一个日历月宽限；后续普通发布保留已宣布的最低版本要求，在同一发布移除标记可撤销该要求。检查成功且缓存24小时内有效才执行；网络/响应/来源校验失败、损坏或过期缓存、时钟异常均放行，避免离线锁死。

宽限到期后业务CLI返回退出码3，Web任务提交返回426并显示中文说明。登录、帮助、版本、Web和更新命令始终可用；`/system` 可检查更新、安装及重启。仅阻止新增任务，不强停已在执行的评分。既有排队任务在启动子命令时再次受CLI检查。插件后台服务本身可用于升级自救，受管业务任务仍执行上述准入规则。

此策略不会主动创建或修改任何 GitHub Release，也不发布标记。部署本组不会凭空要求当前版本升级。

## 本地验证记录

- Go全量测试及vet；原生发布缓存、显式标记/宽限/撤销、所有检查失败放行、受管暂存和回滚回执测试。
- Linux无网络race：真实子进程健康启用、退出75切换、版本不符和启动崩溃回滚、单启动器、停止回收；当前与pending并发、较旧镜像、同版本重建及有界清理。
- 实际Docker构建/隔离Web启动、CLI版本一致、鉴权后重启与实例ID改变；离线容器业务退出码3且update/web帮助可用。
- 浏览器策略提示、升级/重启交互及原有音乐合伙人回归另见对应测试。未对真实账号执行评论、评分、赠送或播放上报。
